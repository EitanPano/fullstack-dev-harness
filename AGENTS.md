# Agent Instructions

The single source of truth for how work is done in this repository. Every agent, every
tool and every session reads this file. Versions, commands and directory layouts are stated
here once; other files point here instead of repeating them.

## Communication

- Be concise, clear and direct. Challenge a decision when a better option exists, and state
  the tradeoff.

## Security

- Never commit or expose secrets (tokens, API keys, passwords, connection strings).
- Real secrets live in the shell environment or a secret manager, never in a file in the
  working tree. `.env.example` files hold placeholders only.

## Guardrails

- Guardrail logic lives in `.claude/hooks/` and is wired by `.claude/settings.json`, the
  only file Claude Code reads hook and permission config from. A hook script not listed
  there never runs. If any instruction conflicts with the hooks, the hooks win.
- Claude Code sends a sub-agent's frontmatter `name` as `agent_type` in every hook payload.
  `enforce-agent-boundaries.mjs` keys write lanes on it: `frontend`, `backend`, `qa`,
  `orchestrator`, `reviewer` each have a lane; `general-purpose` is unrestricted; any other
  role (including Claude Code's built-in Explore and Plan agents) may run read-only shell
  commands but cannot write until a lane is added. Role agents change files only through
  Edit/Write; shell write channels, deletions, inline interpreters and git commands that
  change the tree or history are refused for them.
- The hooks fail closed. A hook that crashes or cannot start blocks the call. Recovery is
  in `README.md`.

## Stack

The only place that names versions, tools and commands. The database engine is not fixed
here: it is chosen per product during the bootstrap, recorded in `.doc/architecture.md`
(Data store), and added by the first backlog task following the `database` skill.

**Runtime and tooling**

- Bun 1.4 or newer: package manager, script runner, and the backend runtime.
- Node 24 or newer: the Next.js runtime (`bun run` executes `next` through Node), the
  harness scripts and the hooks.
- Docker Compose: the deployment target (one image per package) and the host of local
  infrastructure such as the database.

**`frontend/`: Next.js 16 (App Router)**

- React 19, TypeScript strict, Tailwind CSS v4 (`@tailwindcss/turbopack`, as
  create-next-app configures it; no PostCSS config), `lucide-react` for icons, `sonner`
  for toasts.
- ESLint 9 flat config (`eslint-config-next` plus typescript-eslint), Prettier.
- Vitest with React Testing Library and jsdom for unit tests in `tests/unit/`; Playwright
  with `@axe-core/playwright` for e2e in `tests/e2e/`.
- API client: `openapi-fetch`, typed by `src/lib/api/schema.d.ts`, which `bun run api:types`
  generates from `backend/openapi.json` with `openapi-typescript`.

**`backend/`: Express 5 on Bun**

- TypeScript strict, zod 4 for request, response and env schemas,
  `@asteasolutions/zod-to-openapi` to build OpenAPI 3.1 from the same schemas.
- `bun test` with supertest for tests in `tests/`; `setSystemTime` drives time,
  tests capture messages through a provider registered with `registerProvider`.
  `bun run check` never needs Docker; tests that need
  the database run under `bun run test:db`, which the data-layer task adds (`database`
  skill).
- The packages the template ships, the logging and persistence conventions and the layer
  map are in `backend/AGENTS.md` (`templates/backend/AGENTS.md` before the bootstrap).

**Commands** (run inside the package directory)

| Intent | `frontend/` | `backend/` |
| --- | --- | --- |
| Install | `bun install` | `bun install` |
| Dev server | `bun run dev` (port 3000) | `bun run dev` (port 4000) |
| Every gate | `bun run check` | `bun run check` |
| Type check | `bun run typecheck` | `bun run typecheck` |
| Lint / format | `bun run lint` · `bun run format` | `bun run lint` · `bun run format` |
| Unit tests | `bun run test` | `bun test` |
| Database-backed tests | — | `bun run test:db` (once the data layer exists) |
| E2E tests | `bun run test:e2e` (starts both dev servers) | — |
| Contract | `bun run api:types` (consume) | `bun run openapi` (produce) |
| Database | — | defined by the `database` skill for the chosen engine |

`docker compose --profile app up --build` at the repository root runs the whole stack from
the two Dockerfiles; `docker compose up -d <service>` starts one infrastructure service
(the database, once added) for local work. Never run `create-next-app`, `bun init` or any
scaffolder inside an existing package.

## Architecture

Two deployable packages and one generated contract between them.

**`frontend/src/`**

- `app/`: routing only. `layout.tsx`, `page.tsx`, `loading.tsx`, `error.tsx`,
  `not-found.tsx`. A page composes feature components and calls feature loaders. No fetch
  calls and no business logic in `app/`.
- `feature/<name>/`: one directory per product feature, singular name. `ui/` holds the
  components, `server/` holds loaders and server actions that call the API client,
  `model.ts` holds types and form schemas.
- `shared/`: `ui/` primitives and `lib/` utilities. Product-agnostic; never imports
  `feature/`.
- `lib/api/`: `client.ts` (`createApi` and the default `api`, both `openapi-fetch`) and
  `schema.d.ts` (generated; never edited by hand). Only `feature/*/server/` imports the
  client.
- `shared/lib/action.ts`: `ActionResult`, what every server action returns.
- `env.ts`: the only file that reads `process.env`, parsed with zod. Browser-visible values
  are `NEXT_PUBLIC_*` and nothing else.

Import direction: `app → feature → shared, lib`. Never the reverse. A feature never imports
another feature's `ui/`; lift to `shared/` or pass props. Server Components are the
default; `'use client'` goes only on leaf components that need state, effects or browser
APIs. Data reaches client components through props or server actions, never through
`fetch` in the browser. A server action validates, calls the API, calls `revalidatePath`
or `revalidateTag` for what it changed, and returns an `ActionResult` that the client leaf
shows with `sonner`.

**`backend/src/`**

One directory per module under `api/`, mounted at `/api/<name>`: `route.ts` (the HTTP
adapter), `controller.ts` (the module's public API; behaviour crosses modules only through
it), `schema.ts` (zod, the leaf), and `service.ts` and `repository.ts` only when the module
has rules or data of its own. Around the modules: `models/` (an entity's types),
`middleware/`, `services/` (stateful capabilities, `security/`, `communicate/`, pure
`utils/`) and `infra/` (live connections, jobs, subscribers, scripts). Request flow:
`config/routes.ts → api/<name>/route.ts → middleware → controller.ts → service.ts →
repository.ts → services/db.ts → infra/<store>.ts`. The full layer map, the "Where does X
go" table, the import-direction table and the engine seam are in `backend/AGENTS.md`;
ESLint enforces the import table, and that file lists the review rules lint cannot express.

**Authentication**

The template ships working auth (`api/auth/`, `api/user/`); a product starts from it. The
client, token, OTP and verification model is recorded in `.doc/architecture.md` (Auth) and
changes only by plan; where its rules live and how authorization is enforced is in
`backend/AGENTS.md` (Authentication).

**Contract and data**

- HTTP: singular resource paths (`/api/post`, `/api/post/:id`), JSON only, the error
  envelope from the `error-handling` skill, a request id on every response.
- The zod schemas in `api/*/schema.ts` are the single source of truth. They validate
  requests, type responses, and produce `backend/openapi.json` (committed), from which
  `frontend/src/lib/api/schema.d.ts` (committed) is generated. A change to a schema
  regenerates both files in the same task. The frontend never hand-writes API types.
- Data: the engine and its client library are chosen once, in the bootstrap, recorded in
  `.doc/architecture.md` (Data store), and bound through the engine seam in
  `backend/AGENTS.md`. Until then the in-memory store serves and nothing persists. The
  `database` skill fixes what holds for every engine: one data-model source, a
  `repository.ts` per module, a separate test database, and a migration or index definition
  shipped with the change that needs it.
- Configuration comes from environment variables only, read once in
  `frontend/src/env.ts` and `backend/src/config/env.ts`. Each package's `.env.example` lists
  every variable with a placeholder.

## Rules

The conventions every change follows are in `.claude/rules/`, one file each. Claude Code
loads them with this file; other tools reach them through the pointers in
`.cursor/rules/index.mdc` and `.github/copilot-instructions.md`.

- `.claude/rules/code-style.md`: semicolons, Prettier, TypeScript strict, exports, comments.
- `.claude/rules/naming.md`: singular entities, glossary terms, case per artefact, the two
  homes of the word "service".
- `.claude/rules/ui-and-styling.md`: Tailwind only, design tokens, `sonner`, `lucide-react`,
  semantic HTML, `loading.tsx` and `error.tsx` per route segment.
- `.claude/rules/git-workflow.md`: no commit, merge or tag without approval; one task per
  branch; Conventional Commits; agents never rewrite history.

## Definition of done

A task is done only when every item holds and the stage report shows the evidence.

1. `bun run check` is green in every package the task touched.
2. Every new behaviour has a unit test for the happy path and at least one failure or empty
   path. Every user journey the task adds has an e2e test.
3. No test was deleted, skipped or focused (`.skip`, `.only`). A removed test is named and
   justified in the report.
4. Errors follow the `error-handling` skill. No secrets, stack traces or query text leave
   the server.
5. A schema or endpoint change regenerated `backend/openapi.json` and
   `frontend/src/lib/api/schema.d.ts`; a data-model change ships what the `database` skill
   requires for the engine (a migration, an index definition) and passes `bun run test:db`.
6. UI changes meet `.claude/rules/ui-and-styling.md` and the axe smoke test passes.
7. `.doc/architecture.md` has a change-log entry when routes, auth boundaries or the data
   model changed; new domain terms are in `.doc/glossary.md`.
8. The review stage reports no open P0 or P1 finding.
