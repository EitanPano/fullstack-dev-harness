## Goal

Root `.doc/` holds what is true for the whole product. What is true for one package lives in
`<package>/.doc/`, written by that package's agent: every package has an `architecture.md`, every
frontend also a `design.md`. A package's `AGENTS.md` holds the template's rules and no task adds
to it.

Why: a client project on `astro-cloudflare` (one frontend, one Worker, 36 plans in five days)
showed three faults.
- The harness has no home for a design. Its only slot is ten lines in
  `.doc/product-definition.md › Design`, one per product, although several frontends are allowed
  since catalog `v1.15.0`. The project wrote its own `.doc/design.md` (about 4,000 words) and
  wired it in through `.doc/conventions.md`.
- Root `.doc/` collected package knowledge: its `architecture.md` reached about 9,500 words,
  mostly the server's data flow, data model and auth. Only the driver writes `.doc/`, so a role
  agent hands its own facts over in a report line.
- A package's `AGENTS.md` mixed the template's rules with product facts. The Astro template asks
  each task to describe its page there; both package files reached about 6,700 words after the
  project had split them into twelve nested guides with size tests of its own.

## Scope

In:
- The layout `<package>/.doc/` and the three skeleton files the harness writes into a package.
- The split of the root skeletons: `.doc/architecture.md` and `.doc/product-definition.md`.
- The harness text that names who reads and who writes which file.
- The bootstrap walk in two parts, before and after the scaffold.
- In the catalog: every instruction that tells a task to edit a package's `AGENTS.md`; ADR 0019.

Out:
- An `sdk` package kind (a product's public SDK): its own plan. The rule here is per package,
  so it inherits `.doc/`.
- Brand answers per frontend in the catalog's generator (question 1).
- Nested guides beside feature code, `Owns:` lines and size tests in a package (D4).
- Moving an existing project's docs: by hand, from the release notes (D7). No migration command.
- `.doc/glossary.md` and `.doc/conventions.md`: product-wide, unchanged.
- The lanes: a package's agent already writes anywhere in its package; root `.doc/` stays closed
  to role agents.

## Assumptions

Decisions, each Eitan's unless marked as a call.

- D1 — Layout: `<package>/.doc/`. Root `.doc/` is product-wide: `product-definition.md`,
  `architecture.md`, `glossary.md`, `conventions.md`.
- D2 — Root `product-definition.md › Design` is the shared brand; each frontend's look is in
  `<frontend>/.doc/design.md`.
- D3 — (call) "dashboard" is the `admin` frontend type; no type is renamed or added.
- D4 — A package's `AGENTS.md` is the template's: no task appends to it.
- D5 — The harness owns the skeletons and writes them into a package when it is created. (call)
  They live in `scripts/package-doc/`, beside the code that writes them: `bootstrap-project` is
  removed by setup. A written file is the project's; the harness never writes it again.
- D6 — A task records a feature as one change-log line that cites its plan, and in the README's
  Features. The description stays in the plan.
- D7 — Existing projects keep working: the harness cites "`<package>/.doc/architecture.md` (the
  root file where a package has none)", once per citing file. The release notes give the steps:
  run the seeding command, move the sections by hand.
- D8 — (call) What a package's `.doc/` holds:
  - every package, `architecture.md`: what is in the package, and its change log;
  - a server or serverless package's takes Data Store, Data Model, API and Auth from today's root
    file, markers included;
  - a frontend's holds its routes and gated groups, client-side state, the roles as it sees them;
  - a frontend adds `design.md`.
- D9 — (call) Root `architecture.md` keeps Primary Components, Data Flow between packages,
  External Dependencies and Operational Concerns. The change log is per package; a new package or
  a deploy-mode switch is a row or a line in the root sections, as today.
- D10 — (call) `design.md` holds rules of the look: Reference apps and Primary viewport (both
  moved from the root form), Shell, Page patterns, Components, Rules. Never a page inventory: a
  page gets a line only where it departs from a pattern.
- D11 — (call) Writers: a package's agent writes its own `.doc/`; the driver writes only the
  root. A report's `Docs:` line names root items only.
- D12 — (call) A section the first plan decides (Shell) starts as "none yet", never as a FILL
  marker: a marker stops planning.
- D13 — (call) No ignore line: each template's `check` runs `prettier --check .` over Markdown,
  as it does for the package's `AGENTS.md`. Skeletons ship formatted.
- D14 — The release is plan 031's round: catalog `v1.17.0`, harness `v1.5.0`; `minCatalog`
  unmoved. Both repositories reach `dev` first; the lock bump belongs to the round (plan 031,
  step 9). (call) No template takes a second bump: the five this plan touches hold a version
  `v1.17.0` has not released, so each one's entry for it gains a line.

### Approaches considered

1. The harness ships the skeletons (chosen). One copy of each format, beside the agents and
   skills that cite its headings; a small catalog change. Cost: a package generated without the
   harness has no `.doc/`.
2. Each catalog template ships its own `base/.doc/`. A package describes itself; eight copies to
   keep alike, a format change needs a catalog release, and a template update can conflict with
   what the project wrote. Refused.
3. No skeleton, a skill describes the format. Without markers the "ask before planning" gate
   cannot fire; it is how an ad hoc `design.md` appeared. Refused.

For the layout: files at the package root (`DESIGN.md`; the root fills up, no one folder to name)
and root `.doc/<package>/` (role agents still cannot write it, a doc does not move with its
package) were both refused for D1.

## Open Questions

1. Density and default theme are generator inputs, recorded once per product (`answers.brand`,
   `THEME_DENSITY` and `THEME_DEFAULT` in the catalog's `tools/lib/brand.ts`), yet a console and
   a public site may differ. Change the generator to take them per frontend now? Recommended: no.
   They stay in the root brand as the product's defaults; a frontend's `design.md` may state its
   own and its first plan applies them in that frontend's tokens. Per-frontend brand answers
   become a catalog backlog line.
   > No, as recommended (Eitan, 2026-11-23: "recommended to all").
2. A package's `AGENTS.md` writes `.doc/glossary.md` and means the root. How is the package's own
   folder spelled so the two are never confused? Recommended: `.doc/…` always means the root;
   template text writes "this package's `.doc/…`", harness text `<package>/.doc/…`.
   > As recommended (Eitan, 2026-11-23).
3. The bootstrap fills the data model before the scaffold creates the server package that will
   hold it. Split the walk? Recommended: yes. Before the scaffold: the product definition, the
   brand, the glossary and the answers the scaffold takes (stack, data store, auth). After it:
   each package's markers, in its own `.doc/`.
   > Yes, as recommended (Eitan, 2026-11-23).

## Risks

- A seeded file fails a package's `format:check` and so its `check`. The skeletons ship
  formatted (D13); P1 runs `check` on a fresh project.
- Three change logs instead of one: a task that crosses packages writes a line in each. The
  orchestrator reads the touched packages' logs only, which is the saving.
- `design.md` grows per task as `AGENTS.md` did. D10 forbids a page inventory; the frontend
  agent's prompt carries the rule. No size test (D4): the next real project shows whether one is
  needed.
- The two `.doc/` spellings are confused in template text (question 2). V05 and V07 are read line
  by line.
- An existing project on an older template still reads "this file" in its package's `AGENTS.md`
  while the harness says no task appends to it. The agent prompt wins; the release notes name
  the lines to change by hand.
- The bootstrap walk in two parts changes the first-run order (question 3). P1 runs it from a
  fresh clone.
- One round carries two plans: the entity rename waits for this plan, and a fault here holds
  it. Each plan is its own pull request per repository, so either can be reverted alone.
- Between G4 and G5 the harness's `dev` says no task appends to `AGENTS.md` over a pinned catalog
  whose templates still say "this file". The agent prompt wins; the lock bump ends it.
