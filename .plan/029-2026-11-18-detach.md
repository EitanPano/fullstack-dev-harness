## Goal

Starting a project is two steps with one job each, whichever way the folder was made:

```sh
node scripts/detach.mjs        # step 1: no brief, no catalog, no network, no commit
claude                         # step 2: /bootstrap-project <brief>
```

After step 1 the folder holds no file that exists only to develop the harness, and no harness
commit or tag. Step 2 decides the product and never removes harness history.

Today the bootstrap removes the harness's 28 plans halfway through and its 40 test and
contributor files at the end, and a clone keeps the harness's 253 commits and two tags for good
(`--finish` only warns).

## Scope

**In:**

- `scripts/detach.mjs` (new, `dev` group) and its tests.
- `.claude/harness.json`: a `setup` list, the `dev` files the bootstrap still needs.
- `scripts/bootstrap.mjs`: refuses a tree that is not detached; removes no plan.
- `scripts/history.mjs`: `--finish` loses the harness-history warning.
- `bootstrap-project` skill, `README.md`, `CONTRIBUTING.md`: the two steps.

**Out:**

- The auth text and markers in `.doc/` and the server and Compose facts prefilled in
  `.doc/architecture.md` (piece B, its own plan; it needs a check of the catalog templates'
  `AGENTS.md`). The marker step stays in `bootstrap.mjs` until then.
- Any commit by detach, a bypass flag for its guards, a `create` CLI that downloads a release.
- Recording the exact harness commit a clone came from (see Risks).
- The release: this ships with the next harness version (`cutting-a-release`).

## Assumptions

- Detach never commits (Eitan, 2026-11-18). The root commit stays what it is today: the bootstrap
  preflight asks for it and commits on a yes (`bootstrap-project`, section 0).
- Both starts stay: a repository made with `gh repo create --template`, and a clone.
- `setup` is a top-level manifest field, not a fourth group: the updater in a v1.0.0 or v1.1.0
  project reads the release's manifest with its own `manifest.mjs`, which refuses an unknown
  group and ignores an unknown field.
- "Detached" is a fact on disk, not a record: `scripts/detach.mjs` removes itself, and the
  bootstrap refuses while it exists.
- The `.gitignore` dev block stays until `--finish`: it ignores secret files until the generator
  has merged its own lines.

## Steps

### What detach does

Refuses, changing nothing, unless all hold: `.claude/harness.json` loads; `.fullstack/catalog.yaml`
is absent; the folder is the top of a git repository; the tree is clean, untracked files
included (so no removed file holds unsaved work).

It removes the tracked `dev` files outside `setup`, itself included, and the folders left empty.
It commits nothing.

**The harness's commits (answer 4).** A repository made from the template has none, and detach
leaves its git alone: the removals stay as uncommitted changes and go into the scaffold commit.
A clone has them (the manifest's `rootCommit` is in the history, or the clone is shallow). There
detach replaces `.git` with a fresh, empty repository on `main`, after four more guards that
prove nothing local is lost: one local branch, no stash, one worktree, `HEAD` contained in a
remote-tracking branch.

Order in a clone: guards, rename `.git` aside (the one step a lock can refuse, before anything is
lost), remove the files, `git init`, remove the renamed directory. A leftover directory is named
in the output. `--dry-run` prints what would be removed and whether git would be replaced, and
changes nothing.

## Risks

- `.git` is locked (an editor, a watcher, read-only pack files on Windows) — the rename refuses
  before any change; V01 runs on Windows.
- Detach runs in a checkout used to develop the harness — the branch, stash and unpushed guards
  refuse it. A fresh contributor clone would be detached; a new clone restores it, and
  `--dry-run` shows the effect first.
- A clone no longer records the harness commit it came from (today `--finish` writes `HEAD`) —
  the updater falls back to the version's tag, as it already does for a template repository. A
  clone of an unreleased `dev` gets the file list without a diff as its update advice.
- In a template repository the harness's plans and tests stay in its first commit, removed by
  the scaffold commit — accepted: clearing them would rewrite a commit that may be pushed.

## Changes during the task

- Step 7: the detach check is item 2 of the skill's section 0, after the `git init` offer, not
  first. Detach refuses a folder with no repository or with untracked files, so after a fresh
  `git init` the root commit (item 3) comes first; the text says so.
- The unpushed guard checks `HEAD` and the local branch (`git rev-list HEAD --branches --not
  --remotes`), not `HEAD` alone: a detached `HEAD` on a pushed commit hid an unpushed branch
  (test "refuses a clone whose branch holds an unpushed commit behind a detached HEAD").
- Tags are not guarded. A first fix checked every ref; P1 showed it refuses a fresh clone whose
  release tag sits on no branch, and offline a local tag cannot be told from a fetched one
  (41d569b, test "a clone with a fetched tag on no branch still detaches"). A local tag on an
  unpushed commit is lost with the old `.git`.
- A failure after `.git` was moved aside puts it back and names `git restore .` (test "a failure
  after .git was moved aside puts the repository back").
- A clone guard beyond the four: `.git` must be a directory, so a linked worktree is refused.
- Detach's own git commands run with `core.fsmonitor=false`, and `detach.test.mjs` sets it for
  the process: this machine's system git config turns the daemon on. A running daemon does not
  block the rename (checked in a scratch clone and by P1).
- V07's test is named "an undetached tree is refused before anything is fetched; --fetch and
  --help still run"; V10's is "keeps setup to dev files, and no setup script imports a dev file
  outside it".
- Not tested: the rename refusal on a locked `.git` and a leftover `.git-harness-<pid>` (neither
  can be forced on every platform).
