## Goal

A project can hold an SDK package at `sdk-<name>/`, generated from the catalog template
`sdk/browser`, beside any stack, and the bootstrap, `scaffold`, `verify`, the write lanes, the
README and the dev loop work for it. After this plan:

- `sdk` is a fourth template kind, beside `server`, `serverless` and `frontend`;
- the package builds an npm entry (ESM, CJS, types), a CDN loader and a frame (its script and
  document) from one source, on a kernel with feature modules that meet only through it;
- a unit is drawn in an iframe from our origin, which alone decides that it was seen
  (question 5); a Shadow DOM mount is a later, second renderer behind the same interface;
- each of the three server templates has a public, cross-origin, versioned namespace,
  `/api/sdk/v1/`, and serves the SDK's files and its frame document, all only in a project
  that holds an SDK;
- the `frontend` agent writes the package; QA writes its `tests/`;
- a project without an SDK generates the tree it does today.

## Scope

**In** (catalog, `v1.18.0`): ADR 0020; the kind, the `--sdk` argument and the `sdk` selection in
the tools; the namespace and the file serving in `server/bun-express`, `server/python-fastapi`
and `serverless/cloudflare`, a minor each; `sdk/browser` 1.0.0; the cases, guides, READMEs and
changelogs.

**In** (harness, `v1.6.0`): this plan; H1 to H10; the lock bump H11 and P1 after the release.

**Out** (each arrives by need, as a later plan or a project's own task):

- An SDK in a project with no API package, or beside a lone `--template` package.
- A second SDK in one project. The directory is `sdk-<name>` all the same.
- Framework adapters (`<package>/react`), a publish workflow in CI, a namespace per SDK.
- A fixed-version, immutable address for the CDN file, and the integrity hash it allows: it
  needs a store that keeps old builds. The package's guide carries the recipe.
- A role agent of its own for the SDK. The lane follows the kind, so the split is small later.
- An SDK for a runtime other than the browser (`sdk/<other>` is a later template).
- A product's own SDK entities: units, placements, telemetry, the key entity and its console;
  and its server checks on a view (the one-time token, the timing, the scoring: ADR 0020 N6).
- The Shadow DOM renderer and a data-only mode.

## Assumptions

Approved with the design on 2026-11-24 unless a line says otherwise; the frame lines follow
question 5 and S2, accepted with ADR 0020 on 2026-11-25.

- The kind is the template id's prefix, as today (`scripts/provenance.mjs`). The directory is
  `sdk-<name>`, `<name>` a kebab-case glossary term; no `type:` line is recorded.
- `--sdk <dir>=<template>` is the one spelling in the generator, the bootstrap and `scaffold`.
  It needs a stack, as `--frontend` does. No stack lists an SDK in `packages:`.
- The SDK is not a frontend: the one-frontend rule beside a `server` package does not count it,
  and none of the ten frontend invariants binds it. It has no brand case and no deploy mode.
- A reserved selection `sdk` is true when the plan holds an SDK. The server templates gate the
  namespace and the file serving on it, so every other project has no cross-origin surface.
  This differs from `api/admin/`, which always ships.
- The namespace: every endpoint under `/api/sdk/v1/`, in `api/sdk/<entity>/`; its `routes`
  mounts there and applies one gate first, the same in every environment: CORS for this
  namespace only (no credentials), a publishable key in a header resolved to its origins, and a
  rate limit by key and `by_ip` on the template's existing limiter. `CORS_ORIGINS` is untouched.
- The default resolver reads `SDK_KEYS` (`key=origin,origin` pairs); unset, every request is
  refused. A product replaces it with a lookup once it has a key entity.
- Within `v1` the namespace only adds; a breaking change is a `v2` beside it. Old builds stay on
  other people's pages for years.
- The SDK takes types only from the contract, of the paths under `/api/sdk/` alone. `transport/`
  is the one caller of `fetch` on the host side and the frame's sender the one inside it;
  telemetry is JSON sent with `keepalive`.
- The API package serves the loader and the frame's script at `/api/sdk/dist/v<major>/`
  (question 4), `<major>` the SDK package's own major, with a short cache and outside the key
  gate. A release of the SDK moves every host page at once; the kill switch is the answer to a
  bad one.
- The frame document is `GET /api/sdk/frame/v<major>?k=<key>`, answered with `frame-ancestors`
  naming the key's origins (`'none'` for an unknown key) and a strict policy of its own. Like
  the files it is outside the OpenAPI document and behind the selection.
- The loader creates the iframe with `sandbox="allow-scripts allow-same-origin allow-popups
  allow-popups-to-escape-sandbox"`, opens a `MessageChannel` handshake to the frame's exact
  origin and collapses the container when no answer comes in time: a refused frame fires
  `load` all the same (S2). No token and nothing that proves a view crosses the channel.
- The frame's meter combines the intersection ratio (half the pixels for a second), the page's
  visibility, its own size and, in Chromium, `isVisible`. A view event carries `occlusion:
  checked | unavailable`; what a view without the check is worth is the product's to decide.
- The messages between loader and frame are a versioned contract in `protocol/`, additive
  within a major; the loader's major is in the frame's address.
- Build order has no cycle: server `contract`, SDK `contract`, SDK build, then the API package's
  image or `assemble` takes the build, as `single` takes a frontend's.
- `verify` already orders by API first and runs a package's `contract`, `check` and `testE2e`
  by the commands it has (`scripts/verify.mjs`), so an `sdk` package needs no new step there.
- The template ships no module and no example: the recipe is its guide's `Adding a feature`
  (ADR 0010). The one endpoint that ships, the kill switch, is real behaviour.
- Harness instruction files stay at their word count or below; `AGENTS.md` is near its cap.

## Open Questions

1. The definition of done asks a frontend for `UI pass:` and QA for `UX:`. What holds for an SDK
   task? Recommended: `UI pass: n/a (no route in UX)`, as the agent file already says for a task
   without a route; the accessibility scan runs on the host fixture once a module renders; the
   rubric grows an SDK check only when a real task shows the need.
   > The recommendation stands: Eitan set the plan active on 2026-11-24 without changing it.
2. Which stack carries P1? Recommended: `react-bun-express`, because the Compose hand-off of the
   SDK's build is the path with the most parts; the Worker's is covered by its case.
   > The recommendation stands (as above).
3. Does `minCatalog` move to `v1.18.0`? Recommended: only if the updater must refuse an older
   catalog; an older one fails `--sdk` with `catalogHint`'s line. Decided at H11.
   > The recommendation stands (as above).
4. S1 found `/sdk/v<major>/` unreachable in `split` and behind the Worker's host router without
   a change in four frontend templates and the router. Serve the file under the API prefix
   instead, at `/api/sdk/dist/v<major>/<file>`? It sits outside the key gate (a script tag
   sends no header) and is the one path under `/api/` that is not JSON. Recommended: yes; no
   frontend template changes, and a missing file answers the error envelope.
   > Under `/api/` (Eitan, 2026-11-24). It replaces `/sdk/v<major>/` wherever this plan and the
   > design name it.
5. The design rendered a unit in a Shadow DOM on the host page. There the measuring code and
   the impression token sit in the publisher's page, so a publisher paid per impression reports
   a view with a few lines of script, on real visitors. Render in an iframe from our origin
   first? Recommended: yes, behind one renderer interface, with the Shadow DOM mount as the
   second renderer for unpaid or trusted uses (research: `.orchestrate/sdk-kind/reports/`).
   > "iframe first, then shadow-dom and do the three engines check" (Eitan, 2026-11-25). S2
   > runs the check; ADR 0020 and the catalog tasks follow its results.

## Contract

The one endpoint the server templates ship, behind the `sdk` selection.

| Endpoint | Request | Response | Errors |
| --- | --- | --- | --- |
| `GET /api/sdk/v1/config` | the key header; `Origin` | `{ enabled: boolean }` | 403 (no key, unknown key, origin not listed), 429 |

Two routes are served beside it and are not in the OpenAPI document: the files at
`GET /api/sdk/dist/v<major>/<file>` and the frame document at
`GET /api/sdk/frame/v<major>?k=<key>` (HTML).

### Spike

S1. A throwaway package and the current documentation of each tool, no account. It settles what
the design left to the builder, and the answers go into ADR 0020:

- one bundler that writes ESM, CJS, types and one IIFE file from one source;
- the tools for the size budget, the public API report and the package lint;
- how the contract tool keeps only `/api/sdk/` paths and writes types alone (else a small
  filter step in the `contract` command);
- a host page under a strict Content-Security-Policy on another origin: a Shadow DOM mount
  styled without an inline style, a `keepalive` request with the key header, its preflight;
- the Worker serving a file under `/sdk/v<major>/` with the cross-origin headers, and the
  Compose servers taking the build in `single` and in `split`;
- whether `build` joins the command vocabulary, and the manifest key that names the CDN output
  so `assemble` and `static` never take the SDK for a frontend.

> Done 2026-11-24, in throwaway folders outside both repositories; Windows only. Run unless a
> line says read.
> - Bundler: tsdown 0.23.7, one config for ESM, CJS, both declaration files and the IIFE. tsup's
>   README calls it unmaintained; Vite's library mode writes no declarations.
> - Gates: `publint` 0.3.25 and are-the-types-wrong 0.18.5 pass on the packed tarball;
>   api-extractor 7.60.1 fails on a changed export and rewrites its report with `--local`; an
>   11-line script holds the size budget with no dependency; a script packs, installs and runs
>   the ESM, CJS and no-DOM consumers in under a second; a `node:vm` check proves one global.
> - `build` is a script of its own: an image or `assemble` calls it to get `dist/`. Whether the
>   manifest's vocabulary gains the word is C1's, by what `assemble` calls for a frontend.
> - Open, for C5: one TypeScript version. The probe ran 7.0.2, where tsdown warns that its
>   declaration generator wants 7.1; the contract tool crashes on 7.0.2 and runs on the 5.9 line
>   the frontends pin. tsdown's declarations on 5.9 are not tested.
> - Contract: `@hey-api/openapi-ts` 0.99.0 with `parser.filters.operations.include` on
>   `/api/sdk/` and the `@hey-api/typescript` plugin alone writes types only; no other schema of
>   the API reaches the output. A schema an SDK path refers to does ship, so SDK shapes get
>   schemas of their own.
> - Host page, in Chromium 159, Firefox 159 and Playwright's WebKit 27.2: the smallest policy is
>   `default-src 'none'; script-src 'self' <file origin>; connect-src <API origin>`, with no
>   `style-src`. `adoptedStyleSheets` and CSSOM (`style.setProperty`) pass; a `<style>` element,
>   a `style` attribute and a linked stylesheet are blocked. An inline loader snippet is blocked
>   without a nonce or hash, so the documented tag is `<script async src>`; the queue stub is
>   for a host that can inline. Under Trusted Types, `innerHTML` and a string `script.src` fail.
> - Telemetry: `fetch` with `keepalive`, the key header and `credentials: 'omit'` arrives after
>   its preflight in all three, from `visibilitychange` and from `pagehide`; Firefox missed a
>   `pagehide`-only listener on close, so both are bound and the buffer is drained once.
>   `sendBeacon` with a JSON body never arrives (it is credentialed). The preflight is cached
>   by `Access-Control-Max-Age` (5 s without it); `cache: 'no-store'` defeats the cache.
> - Failure: with one wrapper (a timeout, every rejection caught) a dead, slow, refusing or
>   CORS-less API leaves no uncaught error in the page. The browser's own console line for a
>   blocked request cannot be suppressed.
> - Cookies: none sent or stored with `omit` in Chromium and Firefox; Playwright's WebKit build
>   sent one anyway, so the namespace ignores cookies on the server.
> - Compose, read: `selectionsFor` (`tools/lib/plan.ts`) and the `@name` markers take a
>   reserved `sdk` selection as they take `single`; the SDK ships a `dist` build target and a
>   `scale: 0` service, the server an `additional_contexts` line, which puts the Compose 2.35.0
>   floor on `split` too. `helmet` sets `Cross-Origin-Resource-Policy: same-origin`, so the
>   file route overrides it. The single-page fallback answers an extension-less miss with
>   `index.html`, so the file route ends in its own 404.
> - Found: `/sdk/v<major>/` is not reachable everywhere. In `split` the server listens on
>   loopback and each frontend's nginx would need a `/sdk/` proxy (Next its own); with several
>   frontends the Worker's host router takes `/sdk/*` first. Every proxy already forwards
>   `/api/` (`location ^~ /api/`, `run_worker_first: ["/api/*"]`). Question 4.
> - Not run: `wrangler dev`. The hook refused it for the sub-agent, which did not route around
>   it. That `_headers` apply to a file fetched through `ASSETS` is read from ADR 0016's spike;
>   the Worker case of C6, or Eitan by hand, is the proof.
> - Not verified: Safari itself, a tab closed from the browser's own UI, Linux.

S2. The iframe mount (question 5), in Chromium, Firefox and WebKit, in a throwaway folder: a
frame from our origin on a publisher's page of another site. Who may embed it
(`frame-ancestors` per key); whether the page can reach the token or click inside; what the
frame's own visibility check reports when the page hides, shrinks, covers, fades or moves it,
and which tricks stay undetected per engine; the resize channel; the `sandbox` set; the host's
policy; a transparent, themed frame; the view sent on unload; a frame moved in the DOM.

> Done 2026-11-25 (Playwright 1.65.1; Chromium 159, Firefox 159, WebKit 27.2, which is not
> Safari; Windows). Run, and the same in all three unless a line names an engine.
> - Embedding: with `frame-ancestors` naming one origin the frame loads there and is blank on
>   any other, nested framing included. A blocked frame still fires `load` and throws nothing,
>   so only a handshake timeout tells the loader, which then collapses the container.
> - Secrecy: the page cannot read the frame's document, a global of it or its `fetch`, and
>   sees no request of it. It cannot click inside: a call or a synthetic event stops at the
>   iframe element, and a real click is `isTrusted` in the frame. What crosses the message port
>   is readable by a page that replaces the loader, so the token never crosses it.
> - Visibility from inside the frame, on a rule of half the pixels for a second: correct for a
>   frame off screen, scrolled out of a container, at 1 px, in a 1 px clipping parent or far
>   left. Wrong (a view is counted) for `visibility: hidden`, any opacity, an opaque cover, a
>   scale transform and a stacked copy in every engine, and for `display: none` in Firefox and
>   `clip-path` in Firefox and WebKit. Chromium's `isVisible` (IntersectionObserver v2) catches
>   every one of those; Firefox and WebKit have no such check. The frame cannot see a scale.
> - So a hidden frame fakes no view in Chromium among the cases tried, and still can in
>   Firefox and WebKit: the event says which checks ran and the server weighs it.
> - Sizing: the frame reports the `html` height from a `ResizeObserver`, the loader sets the
>   iframe's height, 8 to 55 ms after a change, with no scrollbar once `html, body` have no
>   margin. A placeholder of the unit's height avoids the jump.
> - `sandbox`: without the attribute the frame navigates the top page with no gesture. With
>   `allow-scripts allow-same-origin allow-popups allow-popups-to-escape-sandbox` it cannot,
>   keeps its origin (its own `fetch` works, exact-origin messages work) and opens a link in a
>   new tab. Without `allow-same-origin` its origin is `null` and both break.
> - Host policy: `frame-src <our origin>` beside `script-src`; nothing for styles or
>   connections of the frame. A string given to `iframe.src` raises no Trusted Types violation.
> - Look: a frame that declares no `color-scheme` paints white on a dark host; one that
>   declares the host's scheme is transparent; `light dark` is opaque on Chromium and WebKit
>   under a light system setting. Tokens in the frame's address apply at once; `system-ui` is
>   the host's face; a font only the host loaded is not available.
> - Unload: the frame's own view request arrived on navigation, on a closed tab (Firefox by
>   `visibilitychange` alone) and when the loader removed the iframe.
> - A moved iframe reloads its document; `moveBefore` avoids it in Chromium and Firefox.
> - Not tested: Safari, a mobile engine, a tab truly in the background (the tool keeps it
>   visible), a partial opacity against `isVisible`, Chromium's `frame-sizing` beyond a probe.

## Risks

- A script on other people's pages is a supply-chain target, and the namespace is the
  project's first cross-origin surface — the selection keeps it out of every other project; C8
  runs the security pass; H6 sends every later change there to the security review.
- One mutable address means a bad SDK release reaches every host page at once — the kill
  switch, the short cache and "never throws into the host" (V08, V10); the fixed-version recipe
  is in the guide for a project that needs pinning.
- A frame the page hides is still counted as seen in Firefox and WebKit (opacity, a cover, a
  scale, `clip-path`), and a browser driven by a program defeats any renderer — the view event
  says which check ran; the server's checks are the product's (ADR 0020 N6) and the guide
  carries the recipe. The template does not claim a view is proof.
- The server holds one build, so a new major takes the old major's frame from loaders still
  installed, and nothing checks that `protocol/` only adds — the guide's recipe for a store
  of old builds, due before a project's first major; the security review on `protocol/`.
- The spikes ran on Playwright's builds on Windows: Safari, a mobile engine, a tab in the
  background and the Worker's serving of the files are unproven — C6's Worker case; the rest
  is a project's own check before it pays on a view.
- The frame triples what C5 builds (two halves, a channel, a third output) — one renderer
  interface, no module shipped, and P1 as the test of whether the frontend agent can add one.
- Three server templates gain the namespace before a real project has used one — the same
  tests in each (V09), one case each, and P1 on one stack; the other two stay proven by cases.
- The selection's marker lines can change a tree that has no SDK — V12 compares every existing
  case.
- `scaffold` adds the namespace to a server the product has already changed — its three-way
  merge reports the conflict and `ownerOf` hands the server's files to the backend.
- The frontend agent's file is written for routes and screens — P1 is the test; approach B (a
  role of its own) is the fallback, and the lane already follows the kind.
- `AGENTS.md` is near its word cap — H10 replaces words there and measures first.
