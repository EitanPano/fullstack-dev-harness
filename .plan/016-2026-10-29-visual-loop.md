## Goal

This is the second half of Phase 3. After this plan:

- the `ui-design` skill turns the Design brief into page decisions;
- the frontend agent (its UI pass) and QA (its UX pass) apply the skill's rubric to screenshots;
- a plan's UX section names, per route, the pattern, the primary action, the states and the
  copy tone;
- the screens spec checks every screen in both themes with axe, for horizontal overflow and for
  exactly one `h1`, signed-in screens included (OQ1);

- the loop has the speed levers the 60 min goal needs, and P2 measures them.

## Open Questions

Answered by Eitan, 2026-10-29: all four as recommended (OQ1 yes, v1.5.0; OQ2 no, Opus for both
reviewers; OQ3 drafts in `.orchestrate/<slug>/plan.md`; OQ4 yes, P2 in this plan).

1. **Does this plan release catalog v1.5.0?** Recommended: yes. It would contain:
   - screens-spec checks: axe, horizontal overflow, one `h1`, per route and theme;
   - a signed-in screen list;
   - plan 015's catalog docs follow-ups.

   Why:
   - Without signed-in capture, the UI and UX passes judge a sign-in redirect on every gated
     route. That is most of P2's screens: the account, staff publish, booking.
   - Rubric item 8 (dark mode legible) is a contrast measurement, which axe makes exactly and a
     model reading a PNG does not.
   - The reference-module pointers in bun-express's `AGENTS.md` caused one of P3a's three general
     P1s.

   Cost: one catalog PR, release and tag (v1.4.1 took one Sonnet task, an Opus review and a fix
   round). Risk: dark-mode axe finds template defects, which get fixed in the same release.
2. **Should the reviewer's model depend on the task?** Recommended: no. Keep Opus for both
   reviewers and drop this lever.
   - In P3a the two reviewers ran in parallel (322 s and 306 s).
   - D7 makes the security trigger fire on all three P2 tasks (each gates on a role). A Sonnet
     general reviewer would leave the Opus security review on the critical path, so no time is
     saved.
   - Tokens count the same against V5, whatever the model.

   The review lever that does save time is per-package review: about 2–3 min per task, plus
   backend fixes that overlap the frontend build. It changes the review package and the
   fix-round accounting, so it waits for P2's numbers (Out).
3. **Where does a plan live before its task starts?** Recommended: every draft is written to
   `.orchestrate/<slug>/plan.md`, and the driver promotes it to `.plan/` when it cuts the task's
   branch (D8).
   - The alternative is to keep drafts in `.plan/` and have `verify` ignore the other plan files.
     That fails: the commit gate compares the whole tree, so task N's commit would carry task
     N+1's draft.
   - The cost is the hook lane change (H6), made in a worktree.
4. **Is P2 this plan's proof?** Recommended: yes.
   - P2 runs from the branch head after H7, before the harness PR. A one-task P3b cannot show
     pipelining (it needs a second task), and running both P3b and P2 costs a second run of
     about 45 min.
   - The brief stays P1's, unchanged, so the result is comparable. The ledger reports task 1
     apart from tasks 2 and 3, which compare directly with P1b.
   - If P2 misses 60 min but every lever works as designed, the PR still goes ahead and plan 017
     takes the reserve lever.

## Steps

### Decisions

- **D1, the `ui-design` skill (B1).** At most 120 lines, since three agents preload it.
  - Inputs: `.doc/product-definition.md › Design` (Tone, Reference apps, Primary viewport,
    Density), the plan's UX section and the glossary.
  - Page decisions: spec B1's list.
  - Page patterns:
    - the patterns: list, detail, form, auth, dashboard or table, destructive confirm, and the
      empty, loading and error states;
    - each one is composed from the pattern components both frontends ship (`Page`, `PageHeader`,
      `Section`, `EmptyState`, `ErrorState`, `ListSkeleton`, `CardSkeleton`, `AuthCard`,
      `FormActions`, `ConfirmDialog`);
    - the skill covers composition only. Tokens, sizing and primitives stay in the package's
      `AGENTS.md › Styling`, which the skill points to without restating.
  - Copy rules: spec B1.
  - The rubric: spec B1's ten checks.
    - Each check is marked machine-checked (by the screens spec, after OQ1: 2's one `h1`, 7's
      overflow, 8, and WCAG AA) or judged.
    - The passes judge only the judged checks.
  - Severity for QA: a rubric failure is a P2. A broken journey or a WCAG AA failure is a P1.
- **D2, the frontend's UI pass (B2).** A workflow step after the gates.
  - In a task with a backend stage, it runs in the "backend ready" continuation, once e2e has
    captured the screens.
  - It runs only when the plan's UX names a route. Otherwise the report says
    `UI pass: n/a (no route in UX)`.
  - Per route, the agent reads the `phone-light`, `phone-dark` and `desktop-light` screenshots,
    applies the judged checks and fixes what fails. A signed-in route is captured signed in, and
    the agent adds it to the signed-in list (OQ1).
  - One fix pass per route, then the partial `verify` with e2e. What is still open goes to
    `Handoff` for QA, so the pass cannot loop on taste.
  - The report gains `UI pass: <route> — ok | fixed <checks> — <paths>`, one line per route.
- **D3, QA's UX pass (B3).** It replaces `qa.md`'s step 6.
  - It reads the same three screenshots per route and applies the rubric, with D1's severity.
  - `UX: n/a (no phone project)` is dropped (R11).
  - The report line becomes `UX: <route> — PASS|P2|P1 — <check numbers> — <path>`.
- **D4, the plan (B4).**
  - The UX line in `template.md` and `writing-plans` becomes
    `- /<route> — <pattern> — <primary action> — states: loading <…> · empty <…> · error <…> — tone: <…> — phone: <…>`.
  - New required metadata line: `Retired: <exact strings in backticks, comma-separated | none>`.
    It lists the names and paths the task renames or removes (D5).
  - The size caps are unchanged. Answers written under the Open Questions do not count toward
    the 120 lines (P3a: the answers took a 120-line plan to 129).
  - `orchestrator.md` preloads `skills: [writing-plans, ui-design]`.
- **D5, the `retired-terms` check (L2).**
  - Source: the plan's `Retired:` line.
  - What it scans: the end tree, inside the run's package directories (a partial run scans only
    its own), for fixed strings, case-insensitive.
  - What it skips:
    - migrations (`**/migrations/**`, `**/*.sql`);
    - the review package's exclusions (lockfiles, `**/openapi.json`, `**/api/generated/**`);
    - `.plan/` and `.orchestrate/`.
  - It fails listing up to ten `file:line` hits, the way `diffChecks` does.
  - The package's `AGENTS.md` is in scope on purpose: implementers own it (D10).
  - Evidence: P3a's three general P1s, and P1b's role-rename P2s, were leftovers of a rename or a
    removal. Each would have failed the implementer's own partial run.
  - The list is explicit, not inferred from removed identifiers in the diff:
    - an inferred list is noisy and hard to predict;
    - the cost is that a term the plan misses is not caught.

    A legitimate remaining use means the term is too broad. The driver narrows it and records the
    change under `Changes during the task`.
- **D6, the `no-swallowed-assertion` check (L2; plan 014's follow-up).** On a test path, it fails
  on an added line where an `expect(…)` chain ends in `.catch(` (P1b:
  `expect(...).toBeFocused().catch(() => undefined)`), and on a Python
  `except AssertionError` line. A chain split over several lines is not caught; the check's
  comment says so.
- **D7, the security trigger.**
  - A line trigger: a changed line (added or removed) in a code file that names a gate from
    Assumptions fires the trigger, wherever the file is. That file is added to `security.paths`.
  - Two new path globs: `**/*seed*` (privilege tools) and `**/models/user/**` (the auth entity's
    roles). H1 confirms both paths at the tag.
  - `**/auth/ui/**` no longer fires by path (plan 014). A UI file that adds a gate still fires
    by line.
  - The `dev-loop` §4 and `code-review` trigger lists are updated to match.
  - Evidence: in P3a the trigger missed `api/user/routes.ts`, `models/user/enum.ts` and
    `infra/scripts/seed.ts`. It fired only because tests under `middleware/` changed.
- **D8, pipelined planning (L1).**
  - **Drafts.** The orchestrator writes every draft to `.orchestrate/<slug>/plan.md` (OQ3).
    - The size check and the approval run on the draft.
    - When the task's branch is cut, the driver promotes the draft to
      `.plan/NNN-YYYY-MM-DD-<slug>.md`, with the next free number, and writes `Base:` (`git
      rev-parse HEAD`).
    - `verify --plan` reads the promoted file.
    - `dev-loop` §1 and §2 swap: pick the task, plan, approve, then branch and promote.
  - **Lookahead of one.**
    - Once task N's implementers are dispatched, the driver dispatches the orchestrator for the
      next backlog line in the background.
    - The orchestrator gets plan N as in flight: it reads code at plan N's Base (`git show
      <Base>:<path>`), never the working tree being edited. It plans as if plan N's Contract
      and `Retired:` had landed.
    - Draft N+1 is approved (by the human, or delegated) while task N runs.
  - **Landing.**
    - When task N is committed and plan N has entries under `Changes during the task`, the driver
      continues the N+1 orchestrator: "plan N landed as `<commit>` with: …; revise the draft or
      answer `no change`".
    - A revision returns the draft to `Status: draft`.
    - Task N+1's branch is cut from task N's branch.
  - **Saving:** in P3a's numbers, 6.2 + 1.6 min per later task.
  - **Tradeoffs:** a later change to plan N can reach plan N+1, bounded by the landing step. The
    orchestrator and the implementers run at the same time; the token total is unchanged.
- **D9, a final contract (L4).**
  - The contract stage makes every contract change the plan implies, removals and renames
    included. P3a's backend continuation removed the reference module's routes after the
    frontend had generated its types, which cost a `contract-fresh` failure and a relay.
  - Later, the backend changes the contract only when a finding or a blocker needs it. Its
    report then says `Contract: changed`, and the driver sends the frontend
    `contract landed: run contract`.
  - A fix that spans both packages goes to both owners in one message. The frontend stops with
    `Contract: pending backend` until the driver sends `contract landed`, the same pattern as
    §3's e2e.
- **D10, agent hygiene (L5, L7).**
  - **Edit and Write only.** `backend.md`, `frontend.md` and `qa.md` open their lane paragraph
    with "write files only with Edit or Write; never `sed -i`, a heredoc, `>`, `>>` or `tee`".
    P3a had four refusals and four retries, and no report mentioned them.
  - **`Refusals:` line.** Every role report gains `Refusals: <command — the hook's reason, one
    per line | none>`. The driver lists them in its summary.
  - **`Deviations:` line.** Implementer reports gain `Deviations: <plan step not followed as
    written, and why | none>`. The driver copies each one into the plan's
    `Changes during the task` before dispatching the review. An empty section next to real
    deviations drew a P2 in both P1b and P3a.
  - **Package `AGENTS.md`.** Implementers own their package's `AGENTS.md`: a rename or a removal
    updates the lines it invalidates.
  - **The `Commands:` line.** Only names from the `AGENTS.md` command table are recorded. Any
    other command goes in the report's `Handoff` (P3a's `seed`).
- **D11, R15.** Before e2e, `verify` skips a server's dev `migrate` when that server has `e2eDb`,
  because the e2e chain prepares its own database. A 1.x server without `e2eDb` keeps the step.
- **D12, loop-stats segments.**
  - Each agent row splits at its continuations: the dispatch row, then one indented row per
    continuation, each with its start, minutes and tool count. `--json` carries the same data.
  - P2's stage table then comes from the tool instead of hand-written notes.
- **D13, the one-shot intake (C11), in `bootstrap-project`:**
  - **A pasted brief.**
    - The skill fills every form from it, in the user's words.
    - It asks about every gap in one message.
    - It shows one summary to confirm: the forms, the stack, the flags, the brand, the deploy
      mode and the first backlog lines.
    - The section-by-section walk stays for a user with no brief.
  - **Template gaps.**
    - The skill compares the brief's roles, auth rules (password length) and entity names with
      the server template's `AGENTS.md › Auth`.
    - It records each gap in the summary and in `.doc/architecture.md › Auth`, as a decision for
      the first task that needs it. That task's plan carries `Retired:`.
    - In P3a the role rename arrived unannounced, inside task 2's plan.
  - **The tree.** §4 says not to edit the tree while `verify` runs (P1b, P3a).
  - **`--help`.** `bootstrap.mjs --help` prints the usage (P3a: it said
    `unknown argument --help`).
- **D14, the `AGENTS.md` budget.**
  - The Skills table gains a `ui-design` row.
  - DoD item 6 gains "and the `ui-design` rubric (the frontend's `UI pass:` line, QA's UX pass)".
  - Other lines are trimmed so the file stays at 1,200 words or fewer (1,195 now, counted with
    backticks removed).
