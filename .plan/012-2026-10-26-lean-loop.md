## Goal

The design's Phase 1. The dev loop keeps its roles and its two human gates, and loses the
ceremony the eval measured: 74% of loop time spent outside implementation, gates run three times
per task, a red gate travelling under `Verdict: pass`, five Opus reviewers spending 58M tokens to
find one runtime defect, and nine hook false positives.

After this plan:

- one script, `scripts/verify.mjs`, decides whether a task's gates pass. Its exit code and
  `verify.json` are the evidence, keyed to a hash of the working tree, so nobody re-runs a gate
  on an unchanged tree;
- full-stack tasks run contract first, then backend and frontend in parallel, continuing each
  agent with SendMessage instead of re-dispatching;
- one reviewer (plus a security reviewer when the diff touches an auth surface) runs in parallel
  with QA;
- every fix is reviewed;
- plans are capped at 120 lines;
- each task keeps its reports in its own folder;
- the driver writes the change log;
- `AGENTS.md` halves;
- the eval's hook false positives pass.

P1 measures the result on a fresh bootstrap of the same kind of product, through v1's first three
backlog lines, so its numbers compare directly with v1's 151 minutes and 134M tokens.

### Decisions (implementers do not reopen them)

- **D1 `scripts/verify.mjs`** (plain ESM, Node built-ins, named exports, tested with `node --test`
  on fixture repositories):
  - **CLI.**
    - `node scripts/verify.mjs --plan <plan path> [--package <dir>]... [--no-e2e]`, or
      `[--base <commit>] --out <dir>` outside the loop. With no base (a repository with no
      commit yet), the diff checks are recorded as `skipped: no base`.
    - From the plan it reads `Base:` and `Branch:`; the slug is the branch after its first `/`.
    - Output goes to `.orchestrate/<slug>/verify.json`.
    - Exit codes: 0 pass, 1 fail, 2 usage or environment error, which also writes the JSON with
      the reason.
  - **Packages.** Every package in `.fullstack/catalog.yaml`, or those named by `--package`.
    `--package` runs serve the implementers. The driver's run, which the loop branches on, is
    always every package.
  - **Steps, in this order, each recorded:**
    1. The tree hash at start.
    2. Contract freshness: each package's `contract` command, server first. A tree change
       across it means the committed contract was stale. Name the files.
    3. Per package, `check`.
    4. Per package with `testDb`:
       - the `database` service must be listed by `docker compose config --services`;
       - start it with `docker compose up -d --wait database`;
       - then `testDb`, which needs 0 failed and 0 skipped.
    5. Per frontend with `testE2e` (unless `--no-e2e`):
       - the server's `migrate` against the development database, when the command exists,
         after the same `database` check and start as step 4;
       - every package's `http.port` must be free; otherwise fail and name the listening PID.
         `verify` never stops a process it did not start;
       - then `testE2e`. Playwright's `webServer` starts fresh servers, which also resets the
         in-memory rate limiter the eval tripped on.
    6. Diff checks over the added lines of `git diff <Base>` plus the content of untracked
       files:
       - no `.only(`, `.skip(`, `.todo(`, `test.fixme(`, `xit(` or `xdescribe(`;
       - no `pytest.mark.skip`, `skipif`, `xfail` or `pytest.skip(`;
       - no `.exclude(` in an e2e spec.
    7. The tree hash at end. If it differs from the start, the run fails and lists
       `git diff --name-only <start tree>` (OQ2).
  - **Processes.** Each command runs with a timeout:

    | Command | Timeout |
    | --- | --- |
    | `contract` | 3 min |
    | `check` | 10 min |
    | `testDb` | 15 min |
    | `testE2e` | 20 min |

    On timeout or exit, `verify` stops the process tree it started: `taskkill /PID <pid> /T /F`
    on Windows, a process-group kill elsewhere. Nothing it started survives it.
  - **The tree hash.** `git write-tree` through a temporary index copied from `.git/index` and
    refreshed with `git add -A`. Ignored files do not count. The real index is never written.
  - **`verify.json`:**
    - fields: `tree`, `startTree`, `base`, `plan`, `startedAt`, `finishedAt`, `ok`;
    - `packages.<dir>.<step>` = `{ exit, passed, failed, skipped, flaky, ms, log }`;
    - `checks[]` = `{ name, ok, detail }`;
    - `reason` when exit is 2.

    Counts are parsed best effort from bun test, Vitest, Playwright and pytest summaries; the
    exit code rules. A Playwright `flaky` count above 0 fails the step. `log` is the last
    80 lines of a failed step.
  - **Console output.** One line per step (`ok` or `FAIL`, counts, seconds), then
    `verify: PASS|FAIL <tree>`.
  - **Freshness.** `verify` takes `--reuse`. When the current tree equals the last
    `verify.json`'s `tree` and that run passed, it prints `verify: PASS (unchanged since
    <finishedAt>)` and exits 0 without running anything. The driver always passes `--reuse`.
- **D2 `readProvenance`** returns `packages[].dir` (the YAML key) and `packages[].commands`, a map
  of command name to command line, with folded lines joined. Existing callers are unchanged.
  Tests add a folded `testDb` and a package with no `testDb`.

  - (b) `block-secret-file-access.mjs`: in a `grep`, `egrep`, `fgrep`, `rg`, `findstr` or

    `node - <<'EOF'` body.

## Risks

- **`verify` becomes the single point of failure.** A parsing bug that reports green would let a
  red suite through. Mitigation: the exit code rules, not the parsed counts; every failure mode
  has a fixture (V01); the counts are informational.
- **Parallel implementation creates rework** when the frontend builds against a contract the
  backend then changes. Mitigation: the contract stage is the only schema writer after approval.
  The backend's report must say `Contract: unchanged since contract stage`, and `verify`'s
  freshness step catches drift.
- **One reviewer misses what five caught.** The C3 replay on v1's diffs is out of scope, so this
  is checked only on new code. Mitigation: the triggered security reviewer; the `Mechanize:`
  route for repeat classes; the Opus final review of P1's three task diffs, whose findings are
  compared with the loop reviewer's in the notes (v1 found 7 P1s in these three tasks). If the
  final review finds a P0 or P1 that the loop reviewer missed, Phase 3 adds a mode back.
- **Relaxed inline interpreters for orchestrator and reviewer** widen what an accident can do.
  Mitigation: limited to two roles without implementer lanes; shell write channels stay
  refused; documented in `AGENTS.md › Guardrails`.
- **The `AGENTS.md` cut drops a rule someone relied on.** Mitigation: the move table in the
  ledger, V08, and the Opus final review reading the old and new text side by side.
- **SendMessage or `paths:` behave differently from the assumptions.** Mitigation: V24 checks
  them in P1. The fallback for continuations is a fresh dispatch carrying the report path,
  which is v1's cost and no worse.
- **The proof app's e2e still runs on the v1.3.0 template**, now fresh-servered by `verify`.
  Mitigation: P1 measures the loop, not the template. A flake there is logged as `[gate-env]`
  and feeds Phase 2.
- **The proof brief is new text, not v1's prompt**, so the product definitions differ in wording.
  Mitigation: the same domain, stack and three backlog lines word for word. The comparison is
  on loop cost, and the notes record any difference in scope.
- **Another stack holds the proof's ports**, for example a running v1 app. Mitigation: `verify`
  names the PID and the driver stops; nothing outside the proof is stopped. The generated
  Compose file is named after the project (`name: <--name>`), so the brief uses
  `--name proof-studio`, which no other project uses, and the proof gets its own containers and
  volumes.
