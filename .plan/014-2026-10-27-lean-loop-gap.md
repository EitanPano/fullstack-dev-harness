## Open Questions

1. **Can a partial run's results satisfy the driver's full run?** Recommended: yes, per package.
   A step result is reused when its key matches: the package's subtree hash, the shared-input
   hash, the command line and the Base. That makes plan 012's R5 ("partial never satisfies
   reuse") obsolete for package steps. The cross-package checks (contract freshness, diff
   checks, tree-unchanged) always run; they are fast.
2. **Which paths trigger the security reviewer?** Recommended:
   - **Trigger:** auth, session, security and middleware code; `proxy.ts`; `shared/auth/`; the
     env modules; `Dockerfile`; `docker-compose.yml`; CORS configuration.
   - **No longer a trigger:** migrations and `.sql` files. Data-model changes stay with the
     general reviewer, whose checklist already covers them (`code-review` priorities 1 and 2).
     The `database` skill's rules for migrations are unchanged.

## Steps

### Decisions

- **D1, per-package reuse in `verify`:**
  - Each step result in `verify.json` and `verify-partial.json` records its key: the package
    subtree hash, the shared-input hash, the command line and the Base. A later run, full or
    partial, reuses a passing step whose key matches, and prints `reused (<file>, <time>)`.
  - Failing steps are never reused.
  - The cross-package checks always run.
  - A docs-only change (outside every package and every shared input) therefore re-runs only
    the cheap checks.
  - The commit gate still requires the full run's `tree` to equal `git write-tree`. Reuse
    changes what runs, not what is asserted.
  - Tests: reuse across a partial run then a full run; invalidation by a package change, a
    shared-input change, a command change and a Base change; a failing step never reused.
- **D2, the narrowed security trigger** (OQ2), in `scripts/verify/security.mjs` and the
  dev-loop text.
- **D3, the reviewer reads a review package:**
  - `verify` (a full run with a Base) writes `.orchestrate/<slug>/review.diff`: the stat
    summary, then `git diff -U10 <Base>` of the tree it verified, untracked files included,
    lockfiles and generated files excluded.
  - `reviewer.md` and `code-review` say: read that file once, inspect code outside it only for a
    named risk, one check per risk, and do not re-run the suites (`verify.json` is the
    evidence).
  - The fix-diff re-review gets its own package: `verify` writes `review-fix-<n>.diff` against
    the round base.
- **D4, QA formats its own files:** `qa.md` runs the package's `format` command on the test files
  it adds, then the test runner on them, before reporting. `writing-tests` says the same.
- **D5, failing tests in the contract stage:** the backend's contract stage writes the request
  schema tests that must fail (one per validation rule the plan names) before it writes the
  schemas. `backend.md` and the dev-loop's §3.1 say so; `writing-tests` drops the implicit
  exemption.

## Risks

- **A stale reuse.** A step reused on a key that missed an input would let a red suite pass.
  Mitigation: the key includes the shared inputs; the commit gate's tree check is unchanged;
  tests cover every invalidation; when in doubt, an input joins the shared set.
- **A narrower security trigger misses a vulnerability.** Mitigation: the general reviewer's
  checklist puts security first, and now names the data-model items (grants and roles,
  destructive statements, new personal-data columns). The trigger covers auth, session,
  security, middleware, proxy, CORS, env and deploy configuration; per-endpoint gates in a
  module's routes file and the server wiring stay with the general reviewer, as before (they
  change on every API task). The Opus final review of each PR still reads all of it.
- **A reviewer limited to the package misses context.** Mitigation: named-risk checks outside
  the diff are allowed. The plans 012 and 013 reviews used exactly this method and found every
  Critical issue the final reviews later confirmed.

- **D1 interface.**
  - Reuse is on only with `--reuse`; the driver and the implementers pass it.
  - A step's key is computed from the start tree and again from the end tree; the step is
    reusable only when it passed and both keys are equal.
  - `testE2e`'s key covers every package; `migrate` is never reused and runs only with a

  - The shared inputs are `docker-compose.yml`, `db/`, `.fullstack/catalog.yaml`,

  - A package that git cannot resolve is never reusable. Malformed result files are ignored.
  - Partial runs carry forward the other packages' entries.
  - The key does not cover environment variables, git-ignored `.env*` files or toolchains;
    after changing one, run without `--reuse`. Hashing `.env` would make `verify` read secret
    files.
- **D2.** The trigger also covers `**/session/**`, `**/*session*`, `**/cors.*`,
  `**/nginx/**`, `**/.dockerignore` and `**/next.config.*`.
- **D3.**
  - Fix rounds pass `--round <n> --round-base <tree>`, and a `--round` run skips the whole-run
    shortcut.
  - The package fails closed on a git error.
  - Lockfiles, generated files and secret-named files are kept out of the body but listed.
  - A re-review's input is `fix-diff: .orchestrate/<slug>/review-fix-<n>.diff`.
- **D4.** `format` runs over the whole package. QA then lists `git diff --name-only <tree>`
  (the `tree` in `verify.json`), and any file outside its lane goes to the driver as a finding.
