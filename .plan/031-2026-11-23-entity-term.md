## Goal

One word, `entity`, names the unit a server is built from, in both repositories and on every
frontend; the sample a developer copies is named for it; and a library facade has one home,
`services/`, on every frontend.

Why: today two words name one noun (`naming.md` and `models/<entity>/` say entity; `api/<module>/`
and three frontends say module), the word "facade" names two different files, and the frontends
disagree on where a library wrapper lives.

## Scope

In:
- The word, in the harness's live instruction files and in the catalog's templates, lint
  messages, tools and contributor docs.
- The heading `Adding a module` → `Adding an entity` (a contract between the repositories).
- The sample: `api/module/`, `models/module/`, table `module`, route `/api/module` and its
  identifiers → `entity`, in the three server templates, their contracts and migrations, and the
  five frontends' generated clients and tests.
- Frontend wording on React, Vue and Angular; one line on Astro.
- Library facades out of `shared/utils/` into `services/` on React, Next, Vue and Angular, with a
  facade tier in each lint config.
- A catalog ADR (0018) that records D1 to D9 and amends ADR 0012 and ADR 0013 (F2, F9).

Out:
- The `api/` folder and the file names `routes`, `controller`, `schema`, `service`, `model`.
- "Module" in its language sense: an ES or Python module, `type="module"`, tsconfig `module`,
  import-linter's `source_modules`, "the env module", "module scope".
- History: `.plan/001` to `030`, the catalog's ADRs 0001 to 0017 and existing changelog entries.
- Existing projects: nothing renames their packages. A template's changelog lists the renames
  for a developer who wants to do it by hand.
- A wrapper that is a component (`shared/components/icons.ts`, the toaster, the UI kit folder,
  the form folder, Next's theme) and Vue's service-worker library in its store: they stay.
- `.claude/worktrees/028/` (a leftover worktree) and the catalog's `.superpowers/` directory.

## Assumptions

Decisions, each Eitan's unless marked as a call.

- D1 — An entity is a domain noun and everything named for it: route `/api/<entity>`, directory
  `api/<entity>/`, `models/<entity>/`, table or collection `<entity>`, a frontend's
  `services/<entity>.*` and `models/<entity>/`. It has the files it needs.
- D2 — (call) `auth` and `health` are entities; `health` is a thin one (routes and a controller).
  No second word exists for a directory under `api/`.
- D3 — (call) The admin namespace keeps its shape: `api/admin/<entity>/`, "an entity like any
  other".
- D4 — The sample is named `entity`: directories, files (`entity.test.ts`, `test_entity.py`),
  route, table, index (`entity_created_at_id_idx`) and identifiers, case preserved
  (`ModuleRecord` → `EntityRecord`, `createModule` → `createEntity`, `moduleTable` →
  `entityTable`, `listModules` → `listEntities`). The harness glossary row becomes
  `entity (reference)`.
- D5 — Frontends: `services/<entity>.service.ts` (`.api.ts` in React, `.ts` in Next and Astro),
  "a read or write on an entity", "one service per entity over the generated SDK" (Vue and
  Angular said "one facade per server module").
- D6 — (call) A directory under `pages/` is a "page folder", written `pages/<name>/`: "one
  directory per entity or screen group". `home`, `not-found` and `forbidden` are a screen group,
  never an entity. "A page module never imports another one" → "a page folder …".
- D7 — "Facade" means only a file that wraps an external library. It lives flat in `services/`,
  named for what it does (`validation.ts`, `date.ts`, `time.ts`), never for an entity.
- D8 — The facade tier. A facade is a file directly in `services/` that the lint config names as
  the one importer of a library. It imports its library and `models/` types, nothing else of the
  app. Every layer may import it, `shared/` and `core/config` included: (call) one lint
  category, keyed on the listed file names and added once to each layer's allow-list, never an
  exception per component folder. Every other file in `services/` (an entity's service, `api.ts`,
  `call.ts`, `client.ts`, `api-error.ts`, `with-copy.ts`) keeps today's rule; `shared/` still
  cannot import one.
- D9 — What moves: `validation.ts` on React, Next, Vue and Angular; `date.ts` on React and Next;
  `cn.ts` on React and Next (see question 1). (call) A library is an npm package; a platform API
  is not. A helper that imports no package stays in `shared/utils/` (`next-path.ts`,
  `initials.ts`, `storage.ts`, `phone.ts`, `relative-time.ts`, Vue's and Angular's `time.ts`).
  Astro's
  `services/validation.ts` is already there.
- D10 — One catalog release; the harness keeps `minCatalog` at `v1.5.0` and names the old
  heading once per citation: "`Adding an entity` (`Adding a module` in older packages)". The
  clause goes when `minCatalog` passes the release.
- D11 — (call) Versions, read on the catalog's `dev` on 2026-11-23 and confirmed at G4. A major
  where files move in a generated project: `bun-express` 3.2.0 → 4.0.0, `python-fastapi` 2.2.0 →
  3.0.0, `serverless/cloudflare` 2.1.1 → 3.0.0, `react` 6.0.0 → 7.0.0, `next` 4.0.0 → 5.0.0,
  `vue` 4.0.0 → 5.0.0, `angular` 4.2.0 → 5.0.0. `astro` 1.1.0 → 1.1.1 only if one of its files
  changes (its committed client and smoke test are checked at G2). Catalog `v1.17.0`; harness
  `v1.5.0`.
- D12 — (call) The sample's files are renamed by a script that moves tracked files only
  (`git mv`; never a `__pycache__`), limited to the sample's paths and its identifier family;
  contracts, clients and the D1 migration are regenerated by each template's own command; prose
  and lint messages are edited by hand.
- D13 — (call) The harness's word change and its lock bump are one pull request, merged after
  the tag: `dev` never holds "entity" instructions over a catalog that says "module".

### Approaches considered

1. One catalog release, the harness bridged (chosen). Existing projects keep taking harness
   updates; their skills say "entity" while their own package says "module" until a developer
   renames it. Cost: one clause in three harness files.
2. One catalog release, a hard cut: harness `v2.0.0` with `minCatalog` at the release. Clean
   text; every existing project is frozen on harness `v1.3.x`, because a project's
   `catalog.lock` never moves. Refused: a word is a weak reason to end updates.
3. Two catalog releases, the word first and the facades second. A lint regression in the facade
   tier cannot hold the rename; two full release rounds. Refused: the two parts are separate
   pull requests in one release instead.

For the facade tier: a `services/facades/` folder (obvious on disk, one more level, Astro moves
too) and opening all of `services/` to `shared/` and `core/config` (a shared control could call
the API; `core/config` and `services/` would import each other) were both refused for D8.

## Risks

- A replace that reaches a language-sense "module" breaks a config silently (`source_modules`,
  tsconfig `module`, `type="module"`, `worker-configuration.d.ts`). The script takes the sample's
  paths and identifier family only (D12); V01 names exact strings, not the bare word.
- On Windows a working directory spelled `C:\dev` makes Bun's `import.meta.main` false: `openapi`
  and `migrate` exit 0 and write nothing. Run from the on-disk spelling; V03 requires the new
  path to be present, not only a clean tree.
- `Entity` is a generic identifier. Postgres and SQLite do not reserve `entity`; a clash with a
  library type shows in `typecheck` (V02).
- The facade tier opens part of `services/` to `shared/`. It keys on file names listed in lint,
  so a facade added without its lint line is refused from `shared/` (safe side), and the refused
  case in V05 proves an entity's service stays out of reach.
- React and Vue import the validation facade first in the entry file for the CSP (`jitless`);
  the tests that pin that order pin the path too (pull request 2, step 4).
- An existing project that updates the harness reads "entity" in skills and "module" in its own
  package. The bridge clause names the old heading; nothing else is cited by name.
- A changed skill description may fire differently (question 3).
- Two renames in one release: they are separate pull requests, so either can be reverted alone.
