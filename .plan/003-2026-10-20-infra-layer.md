## Goal

Eitan's instruction (2026-10-20): the server template gets an `src/infra` folder
responsible for bootstrapping, connecting, reconnecting and logging for the database, the
cache database and the logger; and the entry file is `index.ts`, which imports
`server.ts`, structured to best practices. After this plan a scaffolded backend starts
its infrastructure before it listens, stops it cleanly on a signal, reports readiness,
logs through one module, and gives the data-layer task and a later cache task a defined
home under `infra/` instead of an ad-hoc `db/` directory. The template still persists
nothing and names no engine: plan 002's engine-neutral decision holds.

## Assumptions

- A1 — The template ships no engine and no cache (plan 002 A1, Eitan's review of plan
  001). `infra/` therefore ships the lifecycle, the logger and an empty resource list;
  the store modules arrive with their tasks.
- A2 — Reconnection after a drop is the driver's job (Postgres pools, the `mongodb`
  driver and Redis clients all reconnect themselves). Infra owns connecting at boot with
  bounded retry, pinging for readiness, and closing on shutdown. Stated in the `database`
  skill so no task re-implements reconnect on top of a driver.
- A3 — Tests import `app` from `src/server.ts` without starting infra (plan 002, V11
  silent request log). Nothing imports `src/index.ts`.
- A4 — Node 24 / Bun 1.4 semantics: top-level `await` in the entry, `server.close()`
  for draining, `SIGTERM`/`SIGINT` handlers. On Windows a signal cannot be delivered to
  a process from another process, so graceful shutdown is proven in the container
  (`docker stop` sends `SIGTERM`), not on the host.

## Open Questions

1. Does the template itself carry Redis-shaped cache code, or only the slot
   (`infra/cache/` defined in the `database` skill, filled by a backlog task)?
   Recommended: the slot. A cache client in the template reverses the engine-neutral
   decision and ships code every product without a cache has to delete.
2. Is a readiness endpoint part of this change? Recommended: yes, `GET /api/health/ready`
   returning 503 with the readiness body when any resource ping fails. Without a
   consumer, `ping()` is dead code; with one, the compose `depends_on` and any
   orchestrator can wait for the store. `GET /api/health` stays liveness and never
   reports a store, so a database outage never restarts the API.
3. Who may touch a store? Recommended: only `api/<name>/repository.ts` and `model.ts`
   import `infra/db/**` and `infra/cache/**` (cache-aside is a data-access concern);
   anything may import `infra/logger.ts`; `lib/` imports nothing from `infra/`. Enforced
   by lint zones.

## Steps

### Contract

| Endpoint | Request | Response | Errors |
| --- | --- | --- | --- |
| `GET /api/health` | none | `{ status: 'ok', uptimeSeconds, version }` (unchanged) | 500 |
| `GET /api/health/ready` | none | 200 `{ status: 'ok', resources: { [name]: 'ok' } }`; 503 `{ status: 'degraded', resources: { [name]: 'ok' \| 'down' } }` | 500 |

The 503 body is the readiness report, not the error envelope: the body is the diagnostic
and callers read the status code. Both responses are registered in OpenAPI under the one
`Readiness` schema. With the empty resource list the endpoint answers 200 and `{}`.

### Backend template (`templates/backend/`)

1. `src/infra/lifecycle.ts`: `type Resource = { name: string; connect(): Promise<void>;
   ping(): Promise<void>; close(): Promise<void> }`; `startInfra(list = resources)`
   connects in list order, each with bounded exponential retry (10 attempts, 500 ms base,
   5 s cap; the compose store may not accept connections yet), logs each failed attempt
   at `warn`, and on final failure closes what connected and rethrows;
   `stopInfra(list = resources)` closes in reverse order and never throws (a close
   failure is logged); `infraStatus(list = resources)` pings every resource in parallel
   with a 2 s per-ping timeout and returns `{ [name]: 'ok' | 'down' }`;
   `withRetry(fn, { attempts, baseMs, maxMs, sleep })` is exported, `sleep` injectable
   for tests (C8).
2. `src/infra/resources.ts`: `export const resources: readonly Resource[] = []`, one line
   per resource, the way `server.ts` has one `api.use` line per module. The data-layer
   task adds `db`; the cache task adds `cache`.
3. `src/infra/logger.ts`: `createLogger({ quiet, sink = console })` returning
   `{ info(message, fields?), warn(message, fields?), error(message, fields?, error?) }`;
   one line per call, `key=value` fields appended; `info → sink.info`,
   `warn → sink.warn`, `error → sink.error` with the error object as the second
   argument so the stack prints (C2); `quiet` silences `info` only. The default export
   is `log = createLogger({ quiet: env.NODE_ENV === 'test' })` (C1). The seam where a
   logging library goes if a product ever needs one.
4. `src/middleware/request-log.ts` and `src/middleware/error-handler.ts` log through
   `log` (the test-silence rule moves into the logger; the error-handler test's
   `console.error` spy still sees exactly one call). `src/openapi.ts` keeps `console.log`
   (a script, not the server).
5. `src/server.ts`: app assembly only. Export `app`; remove the `import.meta.main` block
   and the `env` import. Mount `healthRoute`, which now serves `/` and `/ready`.
6. `src/index.ts`: the process entry. `await startInfra()` (on failure: `log.error` and
   `process.exit(1)`), `app.listen(env.PORT)` with the listening line, a `shutdown(signal)`
   that runs once: stop accepting (`server.close()` then `server.closeIdleConnections()`,
   C5), `await stopInfra()`, exit 0; a 10 s timer exits 1 if draining hangs. `SIGTERM`
   and `SIGINT` call it. No development-mode skip.
7. `src/api/health/`: `schema.ts` adds `Readiness` (`status: z.enum(['ok', 'degraded'])`,
   `resources: z.record(z.string(), z.enum(['ok', 'down']))`) and registers
   `/api/health/ready` with `200` and `503` both as `jsonResponse(…, Readiness)` plus
   `errorResponses(500)` (C3); `service.ts` adds `getReadiness(list = resources)`
   returning the body (no HTTP status in the service); `controller.ts` adds
   `makeReady(list = resources)` and `export const ready = makeReady()`, sending 200 for
   `ok` and 503 for `degraded` (C7); `route.ts` adds `healthRoute.get('/ready', ready)`.
8. `eslint.config.mjs` zones (C6), all over `src/`: `infra/**` never imports `api/**`,
   `middleware/**`, `server.ts` or `index.ts` (it may import `env.ts` and `lib/**`);
   `infra/db/**` and `infra/cache/**` are importable only from `api/**/repository.ts`
   and `api/**/model.ts`; `lib/**` imports nothing from `infra/**`; nothing imports
   `index.ts`; nothing under `src/` imports `server.ts` except `index.ts`. Add
   `./src/infra/**` to the "infrastructure never imports a module" target.
9. `package.json`: `dev` and `start` run `src/index.ts`. `Dockerfile`: `CMD` runs
   `src/index.ts`.
10. Tests: `tests/lifecycle.test.ts` (retry succeeds after transient failures; gives up
    after the attempt limit and closes what connected; stop closes in reverse and swallows
    a close error; status marks a failing ping `down`; all with an injected `sleep`),
    `tests/logger.test.ts` (a quiet logger drops `info` and keeps `warn` and `error`;
    the line carries the fields; the error object reaches the sink), `tests/health.test.ts`
    gains the readiness 200 case through `app` and the degraded 503 case through a probe
    app mounting `makeReady([down])` (C7). `tests/openapi.test.ts` also asserts
    `/api/health/ready`. The scaffold's `openapi.json` and `schema.d.ts` are generated by
    the bootstrap (C4).

## Risks

- `bun run --watch` and the signal handlers: a watch restart may signal the child, and
  the handler drains before exit. Mitigation: `closeIdleConnections()` makes the drain
  immediate when no request is in flight (C5); V03 runs the dev server through
  Playwright. A lagging restart, if it shows up, is a follow-up, not a conditional here.
- A readiness endpoint that pings a store on every call can be hammered. Mitigation:
  `infraStatus` pings in parallel with a short per-ping timeout (2 s); rate limiting is
  the product's concern and out of scope.
- The cache section of the `database` skill is written, not executed, like the engine
  sections in plan 002. Mitigation: it mirrors the Postgres and MongoDB sections one for
  one (service, variable, client file, test instance, reset helper); the first cache task
  runs it through the dev loop like any task.
- Moving `db/` to `infra/db/` changes paths that plan 002 and its skills name.
  Mitigation: V11 grep.
